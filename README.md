# 🏢 Department System — ระบบจัดการสต็อก งานซ่อม บำรุงรักษา และโครงการ

ระบบ Web Application สำหรับงาน IT สำนักงาน แบ่งเป็น **4 โมดูล** ที่ใช้ผู้ใช้งาน/แผนก/ช่าง/ระบบล็อกอินร่วมกัน:

| โมดูล | ทำอะไร | เข้าที่ |
|---|---|---|
| 📦 **สต็อก (Stock)** | ติดตามการนำเข้า/เบิกออกอุปกรณ์, สินค้า, ใบเสนอราคา, รายงานต้นทุน | `/dashboard` |
| 🔧 **งานซ่อม (Repair)** | เปิด/ติดตามใบงานซ่อม (ภายใน/ลูกค้าภายนอก), ช่างซ่อม, ค่าอะไหล่/ค่าแรง, รายงานงานซ่อม | `/repairs/overview` |
| 🗓️ **บำรุงรักษา (Maintenance)** | แผน PM ตามรอบ (ทุก N เดือน), นับวันที่เหลือก่อนถึงกำหนด, ประวัติการบำรุงรักษา, เอกสารแนบต่ออุปกรณ์ | `/maintenance/overview` |
| 📁 **โครงการ (Project Manager)** | ติดตามงานที่มีวันเริ่ม/กำหนดเสร็จ, ไมล์สโตน + ไทม์ไลน์, บันทึกความคืบหน้าพร้อมค่าใช้จ่าย/ไฟล์แนบ, งบประมาณเทียบยอดใช้จริง | `/projects/overview` |

สลับโมดูลได้จาก **แท็บด้านบนหัวจอ (Header)** — Sidebar จะเปลี่ยนเมนูตามโมดูลที่กำลังใช้งานอยู่โดยอัตโนมัติ

> ความต่างระหว่าง **งานซ่อม** กับ **บำรุงรักษา**: งานซ่อมคือ *ตั้งรับ* (ของเสียแล้วจึงเปิดใบงาน) ส่วนบำรุงรักษาคือ *เชิงป้องกัน* (ของยังไม่เสีย แต่ถึงรอบตามปฏิทินแล้ว)
>
> ส่วน **โครงการ** ต่างจากทั้งสองแบบ: เป็นงานที่มี**จุดเริ่มและจุดจบ**ของตัวเอง (เช่น เปลี่ยนแอร์สำนักงาน, ติดตั้งระบบเครือข่ายใหม่) ไม่ใช่ทั้งงานซ่อมที่เกิดจากของเสีย และไม่ใช่รอบบำรุงรักษาที่ทำซ้ำตามปฏิทิน — โมดูลนี้**แยกเดี่ยว** ไม่ผูกกับ `Product`/`RepairJob`/`Equipment` ใดๆ

สร้างด้วย **Next.js 15 (App Router)** + **MySQL** + **Prisma** + **Tailwind CSS**  
รองรับ 2 ภาษา (ไทย/อังกฤษ) แบบสลับได้ทันที

## ⚙️ Tech Stack

| Layer | Tech |
|---|---|
| Framework | Next.js 15 (App Router + Server Actions) |
| Database | MySQL |
| ORM | Prisma |
| Auth | NextAuth.js v5 (Credentials) + bcrypt password hashing |
| i18n | next-intl (ไทย / English, สลับได้จาก Sidebar, จำค่าไว้ด้วย cookie) |
| UI | Tailwind CSS (plain native form controls — no component library in use) |
| Validation | Zod |
| Forms | `useActionState` + Server Actions (no client form library) |
| Charts | Hand-built responsive SVG line charts (no external chart dependency) |
| Export | ExcelJS (.xlsx) + PDFKit (.pdf) — generic column-driven builder ใช้ร่วมกันทั้ง 4 โมดูล (นิยามคอลัมน์อยู่ที่ `reportColumns.ts`); โมดูลโครงการมีตัวสร้าง PDF แยกต่างหากอีกตัว (`projectSummaryPdf.ts`) สำหรับเอกสารสรุป **รายโครงการเดียว** ที่มีหัวข้อ/ย่อหน้า ไม่ใช่ตารางหลายแถวแบบรายงานอื่น |
| Navigation | โครงเมนูรวมอยู่ที่ `src/lib/navigation.ts` (Header tabs + Sidebar อ่านจากที่เดียวกัน) — โมดูลของแต่ละ path เลือกด้วย longest-prefix match |
| Loading UX | `nextjs-toploader` (progress bar ตอนเปลี่ยนหน้า) + Next.js `loading.tsx` (skeleton) + spinner ในปุ่ม/ช่องค้นหา |

## 🚀 การติดตั้ง (Setup)

### 1. Clone และติดตั้ง dependencies

```bash
git clone <repo-url>
cd office-stock-app
npm install
```

### 2. ตั้งค่า Environment Variables

```bash
cp .env.example .env
```

แก้ไข `.env`:

```env
DATABASE_URL="mysql://root:yourpassword@localhost:3306/office_stock_db"
AUTH_SECRET="generate-with: openssl rand -base64 32"
AUTH_URL="http://localhost:3000"
```

> **`DATABASE_URL` ต้องขึ้นต้นด้วย `mysql://` เท่านั้น** — ถ้าคัดลอกมาจากเครื่องมืออื่น (เช่น phpMyAdmin) แล้วติด scheme อื่นมา Prisma จะขึ้น
> `Error validating datasource db: the URL must start with the protocol mysql://` (P1012) และแอปจะไม่ต่อฐานข้อมูลเลย
>
> **ถ้ารหัสผ่านมีอักขระพิเศษ ต้อง URL-encode ก่อน** โดยเฉพาะ `@` ให้เขียนเป็น `%40` ไม่งั้น Prisma จะตัด host ผิดตำแหน่ง:
>
> ```env
> # รหัสผ่านจริง: p@ss123
> DATABASE_URL="mysql://root:p%40ss123@localhost:3306/office_stock_db"
> ```
>
> ตรวจว่า MySQL ฟังอยู่ที่ port ไหนจริงด้วย (`ss -lntp | grep mysql` หรือ `3306` เป็นค่ามาตรฐาน) — ตั้ง port ผิดจะเจอ `P1001 Can't reach database server`

### 3. สร้างฐานข้อมูลและ migrate

```bash
# สร้าง database ใน MySQL ก่อน
mysql -u root -p -e "CREATE DATABASE office_stock_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# Migrate schema
npm run db:migrate

# ใส่ข้อมูลตัวอย่าง (หมวดหมู่, แผนก, ผู้ใช้ demo, สินค้า, รายการตัวอย่าง)
npm run db:seed
```

> seed **ไม่ได้** ใส่ข้อมูลของโมดูลงานซ่อมและบำรุงรักษา — ก่อนใช้งานจริงให้เพิ่ม master list เหล่านี้เองก่อน:
>
> | ต้องเพิ่มที่ | ใช้กับโมดูล |
> |---|---|
> | **ช่างซ่อม** — `/repairs/technicians` หรือ `/maintenance/technicians` | ใช้ร่วมกันทั้งงานซ่อมและบำรุงรักษา — เป็นรายการเดียวกัน แค่มีเมนูให้เข้าถึงได้จากทั้งสองโมดูล |
> | **ประเภทอุปกรณ์** — `/repairs/device-types` | งานซ่อม |
> | **โรงงาน** — `/maintenance/factories` | บำรุงรักษา |
> | **พื้นที่** — `/maintenance/areas` | บำรุงรักษา |
>
> ทุกช่องเป็น optional บนฟอร์ม จึงสร้างงานได้แม้ยังไม่มีข้อมูล แต่รายงานจะขึ้นเป็น `-`
>
> โมดูล**โครงการ**ไม่ต้องเตรียม master list เพิ่ม — ใช้ `Department` ที่มีอยู่แล้ว (optional), ผู้รับผิดชอบ (Owner) ตั้งจากผู้ที่ล็อกอินสร้างโครงการโดยอัตโนมัติ ไม่ใช่รายชื่อที่ต้องเพิ่มก่อน

### 4. รัน Development Server

```bash
npm run dev
```

เปิดเบราว์เซอร์ที่ [http://localhost:3000](http://localhost:3000)

## 👤 Demo Credentials

รันจาก `npm run db:seed` — รหัสผ่านถูก hash ด้วย bcrypt ก่อนบันทึกลงฐานข้อมูลจริง

| Role | Email | Password |
|---|---|---|
| Admin | admin@company.com | admin1234 |
| Staff | staff@company.com | staff1234 |

> ผู้ใช้ทุกคนที่สร้างผ่านหน้า **ผู้ใช้งาน** (`/users`, Admin/Moderator เท่านั้น) จะถูกบังคับให้เปลี่ยนรหัสผ่านในการเข้าสู่ระบบครั้งแรก (redirect ไป `/reset-password` โดยอัตโนมัติ) — บัญชี demo ด้านบนถูก seed มาโดยไม่ติดเงื่อนไขนี้

**Roles ที่มีในระบบ**: `ADMIN` (จัดการทุกอย่างรวมถึงผู้ใช้งาน), `MODERATOR` (เพิ่มผู้ใช้งานใหม่ได้ แต่แก้ไข/รีเซ็ตรหัสผ่าน/ลบไม่ได้ และสร้างได้แค่ role Staff), `STAFF` (ใช้งานทั่วไป ไม่เห็นเมนูผู้ใช้งาน)

> role มีผลเฉพาะกับเมนู **ผู้ใช้งาน** และ**การลบโครงการ**เท่านั้น — ผู้ใช้ที่ล็อกอินแล้วทุก role เข้าถึงได้ครบทั้ง 4 โมดูล (รวมถึงเปิด/แก้ไข/ลบใบงานซ่อม, อุปกรณ์บำรุงรักษา, ประวัติ, master list ทั้งหมด และสร้าง/แก้ไข/บันทึกความคืบหน้าโครงการ) ยกเว้น**ลบโครงการ**ที่ทำได้เฉพาะ `ADMIN` เท่านั้น (ตรวจฝั่ง server ใน `deleteProjectAction`)

## 🔄 รีเซ็ตข้อมูล (Reset Data)

| คำสั่ง | ผลลัพธ์ |
|---|---|
| `npm run db:reset-stock` | ลบรายการนำเข้า/เบิกออกทั้งหมด (`StockTransaction`) และตั้ง `totalStock` ของทุกสินค้ากลับเป็น 0 — **ไม่แตะ** ผู้ใช้งาน/หมวดหมู่/แผนก/สินค้า/ใบเสนอราคา **และไม่แตะข้อมูลงานซ่อม/บำรุงรักษา** เหมาะกับตอนอยากเริ่มนับสต็อกใหม่ก่อนขึ้นใช้งานจริง โดยไม่เสียข้อมูล master ที่ตั้งค่าไว้แล้ว |
| `npm run db:seed` | รันซ้ำได้ (`upsert`) — เพิ่ม/อัปเดตข้อมูลตัวอย่างเดิม ไม่ลบข้อมูลที่มีอยู่ |
| `npx prisma migrate reset` | ⚠️ ล้างฐานข้อมูลทั้งหมดทุกตาราง แล้ว migrate ใหม่ + รัน seed อัตโนมัติ ใช้เฉพาะตอนต้องการเริ่มต้นใหม่ทั้งหมดจริงๆ เพราะลบทุกอย่างรวมถึงผู้ใช้งาน/สินค้า/รายการที่สร้างเองด้วย |

> การลบสินค้ารายตัวจากหน้า **สินค้า** เป็น soft delete (ตั้ง `isActive = false`) ไม่ใช่ลบแถวออกจากฐานข้อมูลจริง เพราะ `Product` ถูกอ้างอิงโดย `StockTransaction` ผ่าน foreign key — ถ้ามีประวัติรายการอยู่ การลบแถวจริงจะ error (`P2003`) เสมอ สินค้าที่ถูกลบจะหายไปจากรายการ/หน้าค้นหา แต่ประวัติ transaction เดิมยังอยู่ครบ

> แผนก (Department) ถูกระบุตอนทำรายการนำเข้า/เบิกออก (ใน `StockModal`) ไม่ใช่ตอนเพิ่มสินค้า — สินค้าหนึ่งชิ้นจึงถูกเบิกให้หลายแผนกต่างกันได้ในแต่ละรายการ

> `Department` ใช้ร่วมกันระหว่างโมดูล **สต็อก** และ **งานซ่อม** — งานซ่อมประเภท **ภายใน (INTERNAL)** ผูกกับแผนก ส่วนประเภท **ภายนอก (EXTERNAL)** กรอกชื่อ/เบอร์ลูกค้าแทน ส่วนโมดูลบำรุงรักษาใช้ `Factory` / `Area` แทน (อุปกรณ์ผูกกับสถานที่ ไม่ใช่แผนก)

> `Technician` ใช้ร่วมกันระหว่างโมดูล **งานซ่อม** และ **บำรุงรักษา** — เป็นรายชื่อชุดเดียว เข้าถึงได้จากทั้ง `/repairs/technicians` และ `/maintenance/technicians`

### สถานะใบงานซ่อม (RepairStatus)

| สถานะ | ความหมาย | นับเป็น | เปลี่ยนไปเป็นอะไรได้บ้าง |
|---|---|---|---|
| `RECEIVED` | รับเครื่องแล้ว รอดำเนินการ | งานเปิด | `IN_PROGRESS`, `CANCELLED` |
| `IN_PROGRESS` | กำลังซ่อม | งานเปิด | `RECEIVED`, `DONE`, `CANCELLED` |
| `DONE` | ซ่อมเสร็จ รอส่งคืน | งานเปิด | `IN_PROGRESS`, `RETURNED`, `CANCELLED` |
| `RETURNED` | ส่งคืนผู้ใช้/ลูกค้าแล้ว | งานปิด | `DONE` (กรณีเปิดงานซ้ำ) |
| `CANCELLED` | ยกเลิก | งานปิด | `RECEIVED` (กรณีเปิดงานซ้ำ) |

- ตารางการเปลี่ยนสถานะที่อนุญาตอยู่ใน `TRANSITIONS` (`src/lib/repair-constants.ts`) และตรวจสอบฝั่ง server — การถอยกลับระหว่างสถานะที่ยังเปิดอยู่ทำได้ (เช่น ทดสอบแล้วไม่ผ่าน `DONE → IN_PROGRESS`)
- `RETURNED` / `CANCELLED` ถือเป็นงานปิด ระบบจะเซ็ต `closedAt` ให้อัตโนมัติ และเคลียร์ค่ากลับเป็น `null` เมื่อเปิดงานใหม่
- งานที่ยังเปิดอยู่และแจ้งมานานเกิน `OVERDUE_DAYS` (ค่าเริ่มต้น **7 วัน**) จะถูกนับเป็น **งานเกินกำหนด** บน Dashboard และหน้าภาพรวมงานซ่อม

### เลขที่ใบงานซ่อม

รูปแบบ `RJ-YYMM-NNN` (เช่น `RJ-2607-001`) เรียงลำดับใหม่ในแต่ละเดือน — ออกเลขภายใน `prisma.$transaction()` เดียวกับตอนสร้างงาน เพื่อไม่ให้เลขซ้ำเมื่อมีคนกดสร้างพร้อมกัน (มี `@unique` บนคอลัมน์เป็นด่านสุดท้าย)

- เข้าสถานะ `DONE` จะเซ็ต `finishedAt` ให้อัตโนมัติ และเคลียร์กลับเป็น `null` เมื่อเปิดโครงการใหม่ — **สถานะกับความคืบหน้าเป็นอิสระต่อกัน**: โครงการเป็น `DONE` ได้ทั้งที่ `progress` ยังไม่ถึง 100% ถ้าไมล์สโตนที่เหลือถูกตัดใจไม่ทำ ระบบไม่บังคับติ๊กไมล์สโตนที่เหลือให้อัตโนมัติ เพราะจะบิดเบือนบันทึกว่างานเสร็จจริงหรือไม่
- เลขที่โครงการรูปแบบ `PJ-YYYY-NNN` (เช่น `PJ-2026-001`) เรียงลำดับใหม่**ทุกปี** (ต่างจากใบงานซ่อมที่เรียงใหม่ทุกเดือน) — ออกเลขภายใน `prisma.$transaction()` เดียวกับตอนสร้างโครงการเช่นเดียวกับใบงานซ่อม

### ความคืบหน้าของโครงการ (Progress) มาจากไมล์สโตนเสมอ

```
progress = round(จำนวนไมล์สโตนที่ติ๊กเสร็จ / จำนวนไมล์สโตนทั้งหมด × 100)
```

- **`progress` เป็นค่าที่คำนวณ ไม่ใช่ค่าที่พิมพ์ได้** — ไม่มีช่องกรอกในฟอร์มใดๆ ทั้งฟอร์มสร้าง/แก้ไขโครงการ คำนวณใหม่ทุกครั้งที่เพิ่ม/ติ๊ก/ลบไมล์สโตน ผ่านฟังก์ชัน `recalcProject()` ที่รันอยู่ใน `prisma.$transaction()` เดียวกับการแก้ไขไมล์สโตนเสมอ กันไม่ให้ `progress` ค้างค่าเดิมถ้าธุรกรรมล้มเหลวกลางคัน
- โครงการที่ยังไม่มีไมล์สโตนเลย `progress = 0` เสมอ (ไม่ใช่ 100%) — แผนที่ว่างเปล่ายังไม่ถือว่าเสร็จ
- `Project.actualCost` คำนวณแบบเดียวกัน คือรวมจาก `cost` ของทุกบันทึกความคืบหน้า (`ProjectUpdate`) ของโครงการนั้น ไม่ใช่ค่าที่กรอกตรงๆ ที่ตัวโครงการ

## 🗓️ การคำนวณรอบบำรุงรักษา

กฎมีข้อเดียว:

```
nextDueAt     = addMonths(วันที่ทำล่าสุด ?? วันที่เริ่มนับรอบ, รอบเป็นเดือน)
remainingDays = nextDueAt − วันนี้        // คำนวณสดทุกครั้ง ไม่เก็บลงฐานข้อมูล
```

- **`nextDueAt` เก็บเป็นคอลัมน์จริง** (มี index) เพราะหน้ารายการต้องเรียงตามความเร่งด่วนและกรอง "ครบกำหนดใน 30 วัน" ด้วย SQL — ถ้าคำนวณสดในโค้ดต้องโหลดอุปกรณ์ทุกตัวออกมาก่อนทุกครั้ง
- **`remainingDays` ไม่เก็บ** เพราะค่าเปลี่ยนทุกเที่ยงคืน เก็บไว้เมื่อไหร่ก็ผิดภายในวันเดียว
- ระบบคำนวณ `nextDueAt` ใหม่ทุกครั้งที่: บันทึก/ลบประวัติการบำรุงรักษา หรือแก้ไขรอบ/วันที่เริ่มนับรอบ — และทำอยู่ใน `prisma.$transaction()` เดียวกับการเขียนประวัติเสมอ ไม่งั้นถ้าพังกลางคันจะเหลืออุปกรณ์ที่กำหนดการไม่ตรงกับประวัติของตัวเอง

### ⚠️ การบวกเดือนต้อง clamp ไม่ใช่ปล่อยให้ล้น

`Date.setMonth` ของ JavaScript จะล้นเดือน — **31 ม.ค. + 1 เดือน ได้ 3 มี.ค.** ไม่ใช่ 28 ก.พ. ถ้าปล่อยไว้ อุปกรณ์ที่รอบตรงกับสิ้นเดือนจะเลื่อนออกไปเรื่อยๆ ทุกรอบ `addMonths()` ใน `src/lib/maintenance-constants.ts` จึงบีบให้อยู่ในวันสุดท้ายของเดือนปลายทาง:

| วันที่เริ่ม | + รอบ | ได้ (clamp) | ถ้าใช้ `setMonth` เฉยๆ |
|---|---|---|---|
| 31 ม.ค. 2026 | 1 เดือน | **28 ก.พ. 2026** | 3 มี.ค. 2026 ❌ |
| 31 ม.ค. 2026 | 3 เดือน | **30 เม.ย. 2026** | 1 พ.ค. 2026 ❌ |
| 29 ก.พ. 2028 | 12 เดือน | **28 ก.พ. 2029** | 1 มี.ค. 2029 ❌ |

การเทียบวันใช้ **เที่ยงคืนตามเวลาเครื่อง** ทั้งสองฝั่ง อุปกรณ์ที่ครบกำหนดตอนเย็นวันนี้จึงอ่านได้ว่า "ครบกำหนดวันนี้" (0 วัน) ไม่ใช่ "เกินกำหนด 1 วัน"

### กลุ่มความเร่งด่วน

คำนวณจาก `remainingDays` ไม่ได้เก็บลงฐานข้อมูล:

| กลุ่ม | เงื่อนไข | สี |
|---|---|---|
| เกินกำหนด | `remaining < 0` | แดง |
| ใกล้ครบกำหนด | `0 ≤ remaining ≤ DUE_SOON_DAYS` (ค่าเริ่มต้น **30** วัน) | เหลือง |
| ตามแผน | `remaining > DUE_SOON_DAYS` | เขียว |
| ปิดใช้งาน | `isActive = false` | เทา — ไม่ถูกนับในสถิติใดๆ |

## 🛡️ Security Notes

1. **Password Hashing**: รหัสผ่านทุกบัญชี hash ด้วย `bcrypt` ก่อนบันทึก ไม่มีการเก็บ plaintext
2. **Race Conditions**: ใช้ `prisma.$transaction()` ป้องกัน concurrent updates
3. **Immutable Logs**: ไม่มี API สำหรับแก้ไข/ลบ StockTransaction
4. **Validation**: Zod validate ทั้ง client + server side, ข้อความ error แปลได้ตามภาษาที่เลือก
5. **Auth**: Middleware ป้องกันทุก route นอกจาก `/login`, บังคับ `/reset-password` เมื่อ `mustResetPassword` เป็น true
6. **Role-based access**: ทุก Server Action ที่เกี่ยวกับผู้ใช้งานตรวจสอบ role ฝั่ง server (ไม่ใช่แค่ซ่อน UI) — Moderator ไม่สามารถแก้ไข/รีเซ็ตรหัสผ่าน/ลบผู้ใช้งานได้แม้จะเรียก action ตรงๆ
7. **Edge-safe middleware**: `src/lib/auth.ts` (มี bcrypt + Prisma) ใช้เฉพาะใน Server Components/Actions เท่านั้น ส่วน `middleware.ts` ใช้ `src/lib/auth.config.ts` ที่ไม่มี provider เพื่อให้รันได้ใน Edge Runtime
8. **ไฟล์อัปโหลด**: เก็บนอก `public/` และ serve ผ่าน route handler ที่ตรวจสอบ session ก่อนทุกครั้ง — ผู้ที่ไม่ได้ล็อกอินเข้าถึงรูปสินค้า/PDF ใบเสนอราคา/ไฟล์แนบงานซ่อมไม่ได้ (ได้ `401`), ชื่อไฟล์ถูกสุ่มเป็น UUID และ path ถูกตรวจกัน directory traversal
9. **Whitelist ชนิดไฟล์**: ไฟล์แนบทุกชนิด (งานซ่อม, เอกสารอุปกรณ์, ใบเสนอราคา) รับเฉพาะ `application/pdf` และจำกัด 10MB/ไฟล์ — ตรวจจาก MIME type ฝั่ง server **ก่อน** เขียนไฟล์ลง disk และก่อนสร้างแถวใดๆ ไม่ใช่แค่ `accept` ใน `<input>` (ตั้งชื่อไฟล์ลงท้าย `.pdf` แต่เนื้อไฟล์เป็นรูปก็ยังถูกปฏิเสธ)
   > **ข้อยกเว้น: รูปภาพสินค้า** (`/products`) ยังรับเฉพาะไฟล์รูป (png/jpg/webp/gif) เพราะแสดงผลเป็นรูปในตารางสินค้า ไม่ใช่เอกสารแนบ
   > ไฟล์รูปที่เคยอัปโหลดไว้ก่อนหน้านี้ยังเปิดดูได้ตามปกติ — การจำกัดมีผลกับการอัปโหลดใหม่เท่านั้น
10. **State machine ฝั่ง server**: การเปลี่ยนสถานะใบงานซ่อมตรวจกับตาราง `TRANSITIONS` ทุกครั้ง — เรียก action ตรงๆ ด้วยสถานะที่ข้ามขั้นก็ถูกปฏิเสธ ไม่ใช่แค่ซ่อนตัวเลือกใน dropdown
11. **กันลบข้อมูล master ที่ถูกอ้างอิง**: ลบช่างซ่อม/ประเภทอุปกรณ์/โรงงาน/พื้นที่ที่ยังมีใบงานหรืออุปกรณ์อ้างถึงไม่ได้ (นับจำนวนก่อนลบแล้วแจ้งกลับ) — ใช้ `isActive = false` เพื่อซ่อนจาก dropdown แทน โดยไม่กระทบประวัติงานเดิม
12. **ชื่อไฟล์ที่ผู้ใช้ตั้งไม่ถูกใช้เป็นชื่อไฟล์จริง**: ชื่อเอกสารและชื่อไฟล์ต้นฉบับเก็บเป็นข้อมูลในฐานข้อมูลเท่านั้น ไฟล์บน disk ถูกตั้งชื่อใหม่เป็น UUID เสมอ — ผู้ใช้จึงกำหนด path ปลายทางไม่ได้
13. **ลบโครงการเป็น ADMIN เท่านั้น**: `deleteProjectAction` ตรวจ `role !== "ADMIN"` ฝั่ง server ก่อนลบเสมอ — ต่างจากทุก action อื่นในโมดูลโครงการ (สร้าง/แก้ไข/บันทึกความคืบหน้า/ติ๊กไมล์สโตน) ที่ทุก role ทำได้ การลบ cascade ไปถึงไมล์สโตน/บันทึกความคืบหน้า/ไฟล์แนบทั้งหมดของโครงการนั้นด้วย
14. **`progress` และ `actualCost` ไม่รับค่าจากฝั่ง client**: ทั้งสองช่องนี้ไม่มี input ในฟอร์มใดๆ เลย คำนวณจาก `recalcProject()` ฝั่ง server เท่านั้น เรียก action ตรงๆ พร้อมส่งค่าทั้งสองนี้มาก็ไม่มีผล เพราะ schema ของฟอร์มไม่รับ field เหล่านี้ตั้งแต่แรก
15. **เอกสารสรุป PDF ต่อโครงการต้องล็อกอิน**: `/api/projects/[id]/summary` ตรวจ session ก่อนสร้างไฟล์เสมอเช่นเดียวกับ route รายงานอื่นๆ — เรียก URL ตรงๆ โดยไม่มี session จะได้ `401` ไม่ใช่ไฟล์ PDF

## 🚢 Deploy สู่ Production

### ขั้นตอนการรัน (ทำตามลำดับ)

```bash
git pull
npm ci                        # ติดตั้งแบบตรงกับ package-lock.json
npx prisma generate           # สร้าง Prisma Client (ไม่มี postinstall script ในโปรเจกต์นี้)
npx prisma migrate deploy     # apply migration กับฐานข้อมูล production (ห้ามใช้ migrate dev)
npm run build                 # ⚠️ ต้องสำเร็จก่อนเสมอ — ดูหมายเหตุด้านล่าง
npm run start                 # รัน Node.js server จริงบน port 3000
```

> **`npm run build` ต้องผ่านก่อนเสมอ** — `next start` ไม่ได้ build อะไรเลย มันแค่อ่านผลลัพธ์ที่ `next build` สร้างไว้ในโฟลเดอร์ `.next/`
> ถ้า build ล้มเหลวแล้วข้ามไปรัน `npm run start` จะเจอ error:
> `Could not find a production build in the '.next' directory`
> ให้ย้อนไปดู output ของ `npm run build` ว่ามี `Error:` อะไร — error ตอน start เป็นแค่ปลายเหตุ
>
> build ที่สำเร็จจะจบด้วยตารางรายการ route (มี `ƒ /uploads/[...path]` อยู่ด้วย)

### ⚠️ อย่ารัน `npm run build` ตอนที่ `npm run dev` ยังทำงานอยู่

ทั้งสองคำสั่งเขียนลงโฟลเดอร์ `.next/` เดียวกัน ถ้า build ทับระหว่างที่ dev server รันอยู่ dev server ที่รันค้างจะพังทันที (ทุกหน้าตอบ `500`) ทั้งที่โค้ดไม่ได้ผิดอะไรเลย — ให้ปิด dev server ก่อนแล้วค่อย build

```bash
# ถ้าเผลอทำไปแล้ว: ปิด process เดิมแล้วเริ่มใหม่
npm run dev        # dev จะสร้าง .next/ แบบ development ให้ใหม่เอง
```

หา process ที่ถือ port อยู่แบบนี้ (ชื่อ process ถูกตัดเป็น `next-server (v1` — `pkill -x next-server` จะไม่แมตช์):

```bash
ss -lntp | grep ':3000'
```

### ⚠️ โฟลเดอร์ `.next/` ไม่ได้อยู่ใน git

`.next/` คือผลลัพธ์จากการ build ถูก gitignore ไว้ — **ทุกเครื่องต้อง `npm run build` เอง**

และ **ห้ามรัน `npm run dev` บนเครื่อง production** เพราะ `next dev` จะเขียนทับ `.next/` ด้วยไฟล์แบบ development ซึ่งไม่มี production build อยู่ข้างใน ทำให้ `npm run start` พังด้วย error เดียวกันข้างบน — ถ้าเผลอรันไปแล้วให้ลบ `.next/` ทิ้งแล้ว build ใหม่:

```bash
rm -rf .next && npm run build      # Windows: rmdir /s /q .next
```

### Environment Variables

`.env` ถูก gitignore ไว้ — **ไม่ได้ติดมากับ `git pull`** ต้องสร้างเองบนเครื่อง production (คัดลอกจาก `.env.example`)

| ตัวแปร | หมายเหตุ |
|---|---|
| `DATABASE_URL` | ชี้ไปที่ MySQL production |
| `AUTH_SECRET` | generate ด้วย `openssl rand -base64 32` — ถ้าเปลี่ยนค่า session ที่ล็อกอินค้างไว้ทั้งหมดจะหลุด |
| `AUTH_URL` / `NEXTAUTH_URL` | โดเมนจริง เช่น `https://your-domain.com` |
| `UPLOAD_DIR` | โฟลเดอร์เก็บไฟล์อัปโหลด (ดูหัวข้อถัดไป) — ถ้าไม่ตั้งจะใช้ `./var/uploads` |

### 📁 ไฟล์อัปโหลด

ไฟล์อัปโหลด **ห้ามเก็บไว้ใน `public/`** เพราะ `next start` จะอ่านรายชื่อไฟล์ใน `public/` แค่ครั้งเดียวตอน server เริ่มทำงานแล้ว cache ไว้ ไฟล์ที่อัปโหลดเข้ามาทีหลังจะไม่ถูก serve จนกว่าจะ restart — จะเจอ error:

```
⨯ The requested resource isn't a valid image for /uploads/products/xxx.png
  received text/html; charset=utf-8
```

(บน `npm run dev` จะไม่เจอปัญหานี้ เพราะ dev อ่าน filesystem ใหม่ทุก request — เป็นเหตุผลที่ bug นี้มักโผล่เฉพาะตอนขึ้น production)

ระบบจึงเก็บไฟล์ไว้ที่ `UPLOAD_DIR` (นอก `public/`) แล้ว serve ผ่าน route handler `src/app/uploads/[...path]/route.ts` ซึ่งอ่านไฟล์จาก disk ใหม่ทุก request, ตรวจสอบ auth, และกัน path traversal — URL ที่ใช้ยังเป็น `/uploads/...` เหมือนเดิม ค่าที่เก็บในฐานข้อมูลจึงไม่ต้องแก้

**ตั้ง `UPLOAD_DIR` เป็น path ถาวรนอกโฟลเดอร์โปรเจกต์** เพื่อไม่ให้ไฟล์ผู้ใช้หายตอน deploy ใหม่หรือ clone ใหม่:

```env
UPLOAD_DIR="/var/lib/officestock/uploads"     # Windows: UPLOAD_DIR="D:\ITStockData\uploads"
```

ระบบสร้างโฟลเดอร์ย่อยเองตามประเภทไฟล์ — จุดที่อัปโหลดไฟล์ได้มีทั้งหมด 4 จุด:

| อัปโหลดที่ | โฟลเดอร์ | ชนิดที่รับ | หลายไฟล์? | ตั้งชื่อเอกสารเองได้? |
|---|---|---|---|---|
| สินค้า (`/products`) | `products/` | **รูปภาพ** png / jpg / webp / gif | ✕ (1 รูป) | ✕ |
| ใบเสนอราคา (`/quotations`) | `quotations/` | **PDF** | ✓ | ✓ |
| ใบงานซ่อม (`/repairs`) | `repairs/` | **PDF** | ✓ | ✓ |
| อุปกรณ์บำรุงรักษา (`/maintenance/<id>/edit`) | `equipment/` | **PDF** | ✕ (ทีละไฟล์) | ✓ |
| โครงการ (`/projects/<id>`) | `projects/` | **PDF** | ✓ | ✓ |

ทุกจุดจำกัด **10MB ต่อไฟล์** และตรวจชนิดไฟล์จาก MIME type ฝั่ง server เสมอ

> **รูปภาพสินค้าเป็นข้อยกเว้นเดียวที่ยังรับไฟล์รูป** เพราะแสดงผลเป็นรูปจริงในตารางสินค้า ไม่ใช่เอกสารแนบ — ที่เหลือรับ PDF อย่างเดียว
>
> ไฟล์รูปที่เคยแนบไว้ก่อนเปลี่ยนนโยบายยังเปิดดูได้ตามปกติ ไม่ได้ถูกลบหรือซ่อน

ถ้าย้ายมาจากเวอร์ชันเก่าที่เก็บใน `public/uploads/` ให้คัดลอกไฟล์เดิมไปไว้ใน `UPLOAD_DIR` โดยคงโครงสร้างโฟลเดอร์ย่อยเดิมไว้

### สิ่งที่ต้องแก้ก่อน build จริงเสมอ

`next.config.ts`:

```ts
serverActions: {
  allowedOrigins: ["localhost:3000"],   // ต้องเพิ่ม domain จริงก่อน deploy
  bodySizeLimit: "10mb",                // ต้อง ≥ ขนาดไฟล์ที่อนุญาต (ใบเสนอราคา + ไฟล์แนบงานซ่อม + เอกสารอุปกรณ์ จำกัดไว้ 10MB/ไฟล์)
```

- ทุกฟอร์มในระบบนี้เป็น Server Action — ถ้าไม่เพิ่ม domain จริงใน `allowedOrigins` การ submit ทุกฟอร์มจะถูกปฏิเสธใน production
- `bodySizeLimit` ต้องไม่ต่ำกว่าขนาดไฟล์ที่ระบบอนุญาต ถ้าตั้งต่ำเกิน (เช่น `1mb`) ไฟล์จะถูกปฏิเสธตั้งแต่ก่อนเข้า validation ของแอป — รูปจากมือถือมักเกิน 1MB
- ค่านี้จำกัด **ขนาด request ทั้งก้อน** ไม่ใช่รายไฟล์ — ฟอร์มงานซ่อมและใบเสนอราคาแนบได้หลายไฟล์ในครั้งเดียว ถ้ารวมกันเกิน `bodySizeLimit` จะถูกปฏิเสธทั้งฟอร์ม แม้แต่ละไฟล์จะไม่ถึง 10MB ก็ตาม (พิจารณาเพิ่มเป็น `20mb`–`25mb` ถ้าเจอบ่อย)

### ข้อจำกัดของ hosting

ระบบนี้ต้องรันบน Node.js server ที่มี persistent disk (VPS/Docker) ไม่เหมาะกับ serverless/edge platform (เช่น Vercel) โดยไม่ปรับโค้ดเพิ่ม เพราะ:
- `bcrypt` เป็น native addon ต้องการ Node.js runtime จริง (ถ้า `npm ci` fail บน Windows ด้วย error เกี่ยวกับ `node-gyp`/`MSBuild` ให้ติดตั้ง build tools หรือเปลี่ยนไปใช้ `bcryptjs`)
- ไฟล์อัปโหลดเขียนลง disk ที่ `UPLOAD_DIR` — serverless/edge มักมี filesystem แบบ ephemeral ที่ข้อมูลจะหายเมื่อ deploy ใหม่ และถ้ารันหลาย instance ไฟล์จะไม่ sync กัน (ดู Next Steps เรื่อง object storage)

## 🧬 Migration ที่มี backfill

migration ส่วนใหญ่แค่สร้างตาราง/คอลัมน์ แต่มี 4 ตัวที่**ย้ายข้อมูลเดิมด้วย** ถ้ารันบนฐานข้อมูลที่มีข้อมูลอยู่แล้วให้รู้ไว้ว่าเกิดอะไรขึ้น:

| Migration | ทำอะไรกับข้อมูลเดิม |
|---|---|
| `add_repair_attachment_doc_name` | ตั้ง `docName = fileName` ให้ไฟล์แนบเดิม ไม่งั้นลิงก์จะแสดงเป็นช่องว่าง |
| `add_maintenance_parts` | ย้าย `cost` เดิมของประวัติบำรุงรักษาไปเป็น `labourCost` เพื่อให้ `cost = labourCost + อะไหล่` ยังเป็นจริง |
| `add_repair_parts` | แปลง `partsUsed` + `partsCost` เดิมของใบงานซ่อมเป็น **รายการอะไหล่ 1 แถว** ที่แก้ไขได้ |
| `add_quotation_files` | ย้ายไฟล์เดี่ยวใน `Quotation.fileUrl` ไปเป็นแถวใน `QuotationFile` (คอลัมน์เดิมกลายเป็น nullable และไม่ถูกเขียนอีก) |

รันตามปกติด้วย `npx prisma migrate deploy` — ทุกตัว idempotent ตามลำดับ migration ไม่ต้องรันมือเพิ่ม

> คอลัมน์เดิมอย่าง `RepairJob.partsUsed`, `MaintenanceLog.partsUsed`, `Quotation.fileUrl` **ยังอยู่ในฐานข้อมูล** และถูกอ่านเป็น fallback สำหรับข้อมูลเก่า ระบบไม่เขียนค่าใหม่ลงคอลัมน์เหล่านี้แล้ว
>
> migration ของโมดูลโครงการ (`add_project_manager_module`, `add_project_requestor`) เป็นการเพิ่มตาราง/คอลัมน์ล้วนๆ **ไม่มี backfill** — ไม่ต้องทำอะไรเพิ่มเมื่อรันบนฐานข้อมูลที่มีข้อมูลเดิมอยู่
